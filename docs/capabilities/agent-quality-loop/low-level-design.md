# Agent Quality Loop — low-level design

This companion owns the Agent Quality Loop package's contracts and implementation constraints. For the capability contract and component flow, see the [overview](README.md) and [architecture](architecture.md).

## 6. Interfaces and contracts

### Immutable terminal receipt

`ConversationAuditRecord.v6` is the server-authored immutable receipt for one terminal managed-Harness turn ([ADR-064](../../decisions/adr-064-retire-planner-era-contracts-and-anchor-the-audit-trajectory.md), [ADR-077](../../decisions/adr-077-carry-the-end-user-identity-to-every-hop-through-token-exchange.md) §6, [ADR-083](../../decisions/adr-083-stream-the-agent-answer-and-govern-it-by-audit-and-evaluation.md)). Its bounded field families are identity (opaque audit reference, canonical correlation identifier, OpenTelemetry trace identifier), attribution (the verified Cognito `sub` as `principal`, carried by every `managed-harness.v3` receipt), provenance (runtime generation, prompt catalog digest, Guardrail version, and the response contract and answer format, `conversation-stream.v4` and `answer.markdown.v1`), outcome (operation, publication, and terminal dispositions, typed failure error and service codes), the trajectory (every governed tool call in order with its disposition and trace anchor, an `errored` attempt with none), publication (custody digest and the released character count), page context (the opaque reference the turn was sent and whether it was used, with a closed reason, never label text, [ADR-120](../../decisions/adr-120-carry-page-context-to-chat-as-a-server-redeemed-reference.md)), and an evaluation-admission reference when a complete turn is admitted. Receipts written before ADR-083 name `public-block-stream.v3` and may also carry a completion-refusal stage, a plan digest, public block kinds and count, finalizer steps with violation codes, and per-step plan selection; they read through v6 with a released character count of zero, and v5 receipts read with no page context. Receipts written by `managed-harness.v1` read through the same contract with no trace and an unanchored trajectory; stored v3 receipts, and v2 receipts, read with no principal.

It excludes question and answer text, session identity, page projection, prompts, model output, tool arguments, evidence payloads and values, rows, and customer identifiers. The normalized correlation identifier is a protected exact lookup attribute, never a metric dimension. The principal lives only inside the stored payload: it is not an index attribute, a metric dimension, a log field, or part of any redacted projection.

One entitled review section returns the principal (ADR-081); see the
[Protected Quality Review API response sections](../protected-quality-review-api/low-level-design.md#response-sections-adr-078-adr-081).
It also mandates a receipt for every terminal class and an expiry on every record; see
[terminal coverage and retention](#terminal-coverage-and-retention-mandated-by-adr-081).

`AuditFinding.v3` appends a versioned structural outcome to one audit identifier, optionally anchored to one trajectory step. Findings contain closed outcome labels, timestamps, and a step ordinal, never evaluator explanations, responses, or prompts. `TurnDeliveryRecord.v1` is the post-stream delivery companion ([ADR-063](../../decisions/adr-063-record-delivery-disposition-for-released-turns.md)); its absence reads as unknown. For a streamed turn its `emitted_block_count` field counts the `text` events the consumer returned for. A streamed receipt derives only turn-level findings, because its trajectory has no finalizer step or plan selection. A distinct producer/version appends a finding; it cannot overwrite the original receipt or another producer's output.

### Exact redacted retrieval

The retained read model accepts only one valid opaque `audit_id` or one normalized UUID4 correlation identifier. Correlation discovery is narrow and every discovered reference is re-attested through a strong exact base-record read before a redacted projection is built. The storage adapter has no scan or broad-filter retrieval path. This is a persistence invariant, not caller authorization: the [Protected Quality Review API](../protected-quality-review-api/README.md) owns the Cognito/custom-authorizer boundary for programmatic retrieval.

### Immutable per-evaluator evaluation linkage

A selected released turn has one ordered, immutable chain under its audit identifier. Configuration provisions the boundaries: `evaluationInput.provisioned` creates the protected source, outbox, dispatcher, and writer; `onlineEvaluation.provisioned` creates the result link and the V4 family (its three evaluators, owned result group, and gate). The V3 family was retired on 2026-09-27 ([ADR-079](../../decisions/adr-079-enable-online-evaluation-only-through-a-verifying-gate.md)). Records written while it ran still decode until they expire, and nothing can release, configure, or dispatch to it. Whether a provisioned family runs is decided by its [release record](#release-records-and-dispatch-adr-079), never by a synth-time flag.

1. The Conversation API persists `EvaluationAdmission.v1` and the outbox row, carrying the exact released answer and its [`GroundedEvaluationContext.v2`](../conversational-runtime/low-level-design.md#6-interfaces-and-contracts), for every complete turn whenever the evaluation plane is provisioned. A turn that ended without `done` is not admitted, even when text reached the screen.
2. The outbox dispatcher reads every family's release record on each run and the turn's ADR-063 delivery companion, and writes `EvaluationDeliveryReceipt.v2`: `dispatched`, naming every family enabled at that run with its configuration identifier and evaluator set, or `not_dispatched` with a closed reason ([dispatch rule](#evaluation-states-dispatch-and-provenance-adr-079)).
3. The protected input writer emits the AgentCore-compatible source span and persists `EvaluationWriterReceipt.v1` with its trace/span custody.
4. Each enabled family's online-evaluation configuration, owned by its [gate](#evaluation-enablement-gate-adr-079), scores the span and writes to the family's owned result group ([result custody](../../concepts/observability.md#37-evaluation-result-custody-adr-079)).
5. `EvaluationResultLinkV3Stack`'s ingress, invocable only by CloudWatch Logs from the owned groups (and by Lambda's own service principal, which runs that delivery), resolves the result's turn, admits it only when its configuration identifier and evaluator match the turn's dispatched delivery receipt, stamps the family, configuration identifier, evaluator revision, model identifier, and prompt digest from that receipt onto canonical `EvaluationResult.v3` keyed by admission and evaluator, and persists it through its projection queue and linker.

A delivery receipt written before the gate (`EvaluationDeliveryReceipt.v1`) is classified as predating it and never decoded as a current receipt, so no result is admitted against it; stored `EvaluationResult.v2` verdicts are not read.

Conditional immutable writes accept only byte-identical at-least-once replay. A missing, malformed, unmatched, or duplicate service event never creates a synthetic result. Evaluation result custody, service telemetry, retention, and reviewer access are owned by [Observability](../../concepts/observability.md); this capability owns only the immutable audit and linkage contracts.

Each companion family is written to its own table by one fixed-name role, and each writer reads back its own write, so a replay is classified as exact ([record-family storage](#record-family-storage-mandated-by-adr-080); what is deployed is stated in its implementation status). Companion items written to the audit table before the move remain there, unread, until their backfilled expiry.

- `infra/lib/constructs/agent-quality/record-integrity.ts` is the only home of each table's writer, each writer input queue's producer, the four action sets, the watched functions and roles, and the event patterns. The table stacks, the two queue stacks, and `RecordIntegrityStack` read it.
- `RecordIntegrityStack` follows `EvaluationEvidenceStack` in `DEPLOY_ORDER`. That covers the owned result groups, the per-family gate and its release records, the dispatch rule and `EvaluationDeliveryReceipt.v2`, admission by receipt with `EvaluationResult.v3` provenance, the ingress's Logs-only invocation (Lambda's own service principal exempt, as on the gate provider), the `QualityEvaluationReview.v3` states, the route's capture whenever the plane is provisioned, and the tamper rules for result groups, release records, function permissions, and the self-watch additions. The V3 family's retirement ([ADR-079](../../decisions/adr-079-enable-online-evaluation-only-through-a-verifying-gate.md), amended 2026-09-27) is part-way through in dev on 2026-09-27: the V3 stack is deleted and V4 is the only enabled family, while the result link still subscribes the V3 group and the remaining retirement deploys (result link, evidence, dispatcher, record integrity, V4, then deletion of the orphaned group) are pending. The gate's calibration is what shows the judge does so. The [no-dispatch alarm](#release-records-and-dispatch-adr-079) is deployed and dev accepted ([validation results](../../../validation/RESULTS.md#evaluation-quality-over-time-adr-079--2026-09-29), 2026-09-29). The live wiring probe and the IAM-simulator custody acceptance, both `make accept-evaluation-custody` ([result custody](../../concepts/observability.md#37-evaluation-result-custody-adr-079) item 1), passed all eleven checks in dev on 2026-10-02: before and after a forced gate refusal, which failed closed and recovered, and after the Harness was recreated ([validation results](../../../validation/RESULTS.md#security-pre-publication-fixes-on-dev--2026-10-02)). Not built, although ADR-079 mandates them: per-evaluator score metrics with their dashboard and alarms, and deletion of the service-created result groups. The tamper pipes' own roles are not in the role-change rule either. Known limits:

- If the dispatcher enqueues a row and stops before settling it, a later run can record that row `not_dispatched`. The result the evaluators still produce is then refused at the ingress and stays unlinked.
- The ingress sends every admissible result in a subscription batch before it asks for a retry of one whose writer or delivery receipt is still absent. The retry sends the whole batch again, and the linker takes the results already sent as exact replays.
- The owned result groups' SSM keys were renamed in one deploy pass, the reader deploying before the old keys are removed, rather than ADR-079 §6's two deploys ([parameters](#evaluation-enablement-gate-adr-079)).
- An evaluator's name carries the environment name, and the service caps a name at 48 characters, so synth refuses an environment name longer than 6 characters. Online evaluation may be provisioned and requested only in dev.
- `EvaluationFamilyV1` keeps the retired V3 value so that receipts and verdicts written while V3 ran still decode. Only the current families (`CURRENT_EVALUATION_FAMILIES`, V4) are accepted by a gate specification, a release record, or a release parameter name. The value is removed once the last V3-era record has expired (2026-12-26 in dev).
- The result link predates the V3 retirement and still carries V3 in its names: `EvaluationResultLinkV3Stack`, its ingress and linker functions, roles, queues, and log groups. They serve every current family. Renaming them replaces the stack, its subscription filters, and the role names the record tables' policies bind, so it is not done.
- A deployment that still has the V3 stack retires it in ADR-079's retirement order, which deploys the result link before the evidence stack, the reverse of `DEPLOY_ORDER`; the [README](../../../README.md) states the step and what fails when it is skipped.

**Upgrade from before ADR-080.** The current state declares TTL and the resource policy on the same table resources, and `DEPLOY_ORDER` deploys the table stacks before every writer stack. Deployed in one step over a deployment from before ADR-080, it lands the policies before the writers move and before the backfill runs: the old writers are refused mid-deploy, the old route keeps writing receipts with no expiry, and statement 2 then refuses the backfill for good. There is no deploy-time guard; such an upgrade is these three steps, in this order:

1. Deploy every stack, in `DEPLOY_ORDER`, from the step-3 state, commit `58cba2c`: the writers moved to their tables, the processor's `INSERT` filter, TTL, and every writer's expiry, with no resource policy and no `RecordIntegrityStack`.
2. Run the [legacy backfill](#legacy-items-and-backfill), first with `DRY_RUN=1`, then for real. **Gate:** the run exits zero with a `failed` count of 0 for every kind. Any failed count blocks step 3: an item left without an expiry when the policies land can never be given one. Keep the printed `moved_family_legacy_expires_at`.
3. Deploy the current state in `DEPLOY_ORDER`, and complete it before that instant, so TTL removes the moved-family legacy items only under the policies.

Dev followed this order on 2026-09-27: `58cba2c`, the backfill, then `0722e4c` and the deploy-time corrections recorded in [validation results](../../../validation/RESULTS.md). A fresh install has no legacy items and deploys the current state directly.

Every per-turn audit and evaluation record family lives in a table whose resource policy admits
exactly one writer role and denies modification and export to everyone.

| Table | Families | Only writer | Stack |
|---|---|---|---|
| Receipts (the existing audit table) | receipt, delivery disposition, evaluation admission | Conversation function role | `AgentQualityStack` (retained) |
| Findings | findings | Agent-quality processor role | `AgentQualityStack` (retained) |
| Evaluation deliveries | evaluation delivery receipts | Outbox dispatcher role | `EvaluationEvidenceStack` (retained) |
| Writer receipts | evaluation writer receipts | Evaluation writer role | `EvaluationEvidenceStack` (retained) |
| Verdicts | evaluation results | Result linker role | `EvaluationEvidenceStack` (retained) |

- Every role a table policy names, writer or reader, has a fixed name, so the policy can name it before the role's stack deploys.
- The evaluation writer and the result linker are not receipts readers. Each receives the receipt's creation time on the message it already consumes, the outbox envelope or the result projection, and computes its record's expiry from it. The time rides as the one `receipt_created_at` SQS string attribute beside the unchanged body: the outbox dispatcher attaches the row's `admitted_at`, which the route's handoff request refuses unless it equals the receipt's `created_at`, and the result ingress attaches the linked receipt's `created_at`. Each consumer refuses and retries a message without exactly that attribute holding a UTC instant.
- The dispatcher also takes its delivery receipt's expiry from the row's `admitted_at`; the processor, a receipts reader, takes each finding's from the receipt it processes.
- Every table keeps `audit_id` as its partition key and the existing item-key shapes. Readers change table, not query.
- Every table has on-demand billing, AWS-managed encryption, point-in-time recovery, deletion protection, and the retained removal policy.
- The receipt table also carries the review API's [turns index](../protected-quality-review-api/low-level-design.md#refusal-storage-access-and-logging-adr-078-adr-080-adr-081).
- The result ingress resolves a result's turn through the receipts table's correlation index and the writer receipts table, then admits it by the turn's delivery receipt in the evaluation deliveries table ([dispatch and provenance](#evaluation-states-dispatch-and-provenance-adr-079)).
- The evaluation outbox is not in this set. It keeps its two writers, the route and the dispatcher's lease.
- The processor's aggregate table holds derived measurements, not a turn's records. It keeps its one writer by IAM only and is outside this set.
- **Order inside the slice:**
  1. the new tables, the fixed role names, and every writer and reader moved to its table, with no resource policies yet;
  2. the agent-quality processor's receipts stream mapping filtered to `INSERT` events, so neither the backfill's updates nor TTL deletions reach it. Unfiltered, it consumes every event and retries a receipt it cannot find;
  3. TTL enabled on every table, then the [legacy backfill](#legacy-items-and-backfill);
  4. the resource policies and the item-change pipes of tamper detection. A policy that landed before step 1 would refuse the still-deployed old writers mid-deploy, and a pipe that landed before step 3 would alarm on every backfill update.
- **Retired in the same slices:** every writer's `PutItem` grant on a table it no longer writes, the stream noise those writes caused on the receipts table, and the readers' queries against the old locations.

**Resource policy.** Every table's policy denies, for every principal whose `aws:PrincipalArn` is not named in the statement, on the table and its indexes:

1. `PutItem` and `PartiQLInsert`, unless the principal is the table's writer role.
2. `BatchWriteItem`, `UpdateItem`, `DeleteItem`, `PartiQLUpdate`, and `PartiQLDelete`, to every principal, the writer included. Expiry is TTL deletion, which proceeds under this deny [verified 2026-09-29, acceptance item 23].
3. Every action that copies data out, to every principal: `CreateBackup`, `RestoreTableToPointInTime`, `ExportTableToPointInTime`, and the Kinesis streaming-destination actions. AWS Backup's `StartAwsBackupJob` and `RestoreTableFromAwsBackup` permissions cannot be denied here: DynamoDB rejects them as invalid policy actions [verified 2026-09-27, a deploy's PutResourcePolicy refusal], so an AWS Backup job is detected, not prevented. Point-in-time recovery is therefore not a standing recovery control: a restore first needs a policy change through CloudFormation, which raises the control-plane alarm below.
4. `PutResourcePolicy`, `DeleteResourcePolicy`, `UpdateTable`, `DeleteTable`, `UpdateTimeToLive`, and `UpdateContinuousBackups`, unless the principal is the stack's CloudFormation execution role, taken from the stack's synthesizer.

The receipts table also denies every item read action (`GetItem`, `BatchGetItem`, `Query`, `Scan`, `ConditionCheckItem`, and `PartiQLSelect`), on the table and its indexes, to every principal except its named readers: the conversation function, agent-quality processor, outbox dispatcher, result ingress, and review function roles. Live acceptance therefore reads receipts through the [review API](../protected-quality-review-api/low-level-design.md#response-sections-adr-078-adr-081), never directly. No statement allows anything; readers are granted by their identity policies. Stream reads are not item reads and fall outside the statement, so the processor and the item-change pipes read the stream as before. The account root can always delete a resource policy and CloudFormation detects no drift on one, so each deploy reads every policy back and the control-plane alarm below covers the time between deploys.

The policies bind roles, not code. A principal that can pass a named role to a new function, or change a named function's code or configuration, acts as that role; the function-change alarm below is the control on that path. `aws:PrincipalArn` compares the role's ARN, so a role deleted and recreated under its fixed name, or given another trust policy, satisfies the same statement; the role-change rule below watches that path.

**Writer inputs.** The policies fix who writes a record, not what the writer was told to write. The evaluation input queue denies `sqs:SendMessage` to every principal whose `aws:PrincipalArn` is not the outbox dispatcher role, and the result projection queue denies it to every principal but the result ingress role. Both statements are deny-only; each producer's identity policy is still its grant. A redrive from either dead-letter queue into its source therefore needs the producer's role [unverified whether a message move task's send is evaluated against the destination queue's policy as the caller]. The ingress's own resource policy allows `lambda:InvokeFunction` only to CloudWatch Logs from this account's owned result groups, and denies `lambda:InvokeFunction` and `lambda:InvokeAsync` to every principal whose `aws:SourceArn` does not match an owned result group (`ArnNotLike`), except Lambda's own service principal. Logs delivers asynchronously, and Lambda re-evaluates the policy as itself when it runs the queued event, without a source ARN; without that exemption every delivery is dropped, and with it a direct invoke, synchronous or asynchronous, is still refused at the API [verified 2026-09-27, dev probe]. An identity-policy grant therefore cannot let a caller invoke the ingress directly and mint a verdict. The directed acceptance path is retired (ADR-079).

**Read back your own write.** Every writer holds `GetItem` on its own table, so a replayed conditional write compares the stored item with its own and reports an exact replay. The evaluation writer's receipt holds the first attempt's emission time, so it reads its stored receipt before emitting the span: a receipt with this message's trace and span is an exact replay and nothing is emitted or written; one with another trace or span is a conflict. The conditional put still decides two concurrent first attempts, and the loser, which has already emitted its span, is retried and then reads as a replay.

**Tamper detection.**

- *Item changes.* Each table's KEYS_ONLY stream feeds an EventBridge pipe, landing with the resource policies in step 4, filtered to `MODIFY` and `REMOVE` records that are not TTL deletions. A TTL deletion carries the DynamoDB service principal in its user identity. The pipe writes to a log group, and a metric filter alarms on any record there. A pipe targets a CloudWatch Logs group directly with its own role [verified 2026-09-27, [Pipes targets](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-pipes-event-target.html)]. The filter spells "not a TTL deletion" as four alternatives over the user identity's type and principal, each absence explicit, because `anything-but` does not match an absent field. A pipe starting at `LATEST` can miss records written while it is being created or updated [verified 2026-09-27, [DynamoDB stream source](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-pipes-dynamodb.html)].
- *Control-plane changes.* An EventBridge rule on CloudTrail management events alarms on every statement 3 and statement 4 action against these tables, whoever calls it, the CloudFormation execution role included. A deploy that changes a policy, TTL, point-in-time recovery setting, or index (such as adding the receipts table's turns index, an `UpdateTable`) therefore raises an expected alarm, which the deploy record acknowledges. So does the ApiStack deploy that first enables the [reviewer access log](../../concepts/observability.md#38-reviewer-access-log-adr-081): enabling HTTP API access logging requires `logs:PutResourcePolicy` of the enabling principal [verified 2026-09-28, [HTTP API logging](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-logging.html)], and the result-group rule matches an account-scoped `PutResourcePolicy`; the first dev deploy made one, by CloudFormation, which the rule recorded [verified 2026-09-28, [validation results](../../../validation/RESULTS.md#review-api-slice-6-commit-a--2026-09-28)]. Two further rules on the same mechanism alarm on the result-group actions that [result custody](../../concepts/observability.md#37-evaluation-result-custody-adr-079) lists, and on a write, delete, or label change of a [release record](#release-records-and-dispatch-adr-079) by any principal but a current family's gate provider role. EventBridge receives these events only while a trail with logging is active in the account. No stack creates a trail; the deploy check reports when none is logging. AWS Backup's permissions cannot appear in a table policy, so a second rule watches AWS Backup's `StartBackupJob` on these tables, and a third watches AWS Backup's own `Backup Job State Change` events by `resourceArn`, which a backup plan's jobs raise without any `StartBackupJob` call [verified 2026-09-27, [AWS Backup EventBridge events](https://docs.aws.amazon.com/aws-backup/latest/devguide/eventbridge.html)]; a job's `CREATED` event carries no `resourceArn`, and its later states do. A restore from an AWS Backup recovery point names the recovery point, not the source table, and is not matched; it needs a backup job first, which is.
- *Function and role changes.* The same mechanism alarms on function creation, code or configuration changes, role passes, event-source mappings created for or repointed at a function, and invoke-permission changes (`AddPermission`, `RemovePermission`, `PutResourcePolicy`, `DeleteResourcePolicy`) for every function that holds a role a table policy or a release-record exemption names, which includes the result ingress and each current family's gate provider. A further rule alarms on `CreateRole`, `DeleteRole`, `UpdateAssumeRolePolicy`, `AttachRolePolicy`, `DetachRolePolicy`, `PutRolePolicy`, and `DeleteRolePolicy` naming any of those roles, each current family's evaluation execution role, or the CloudFormation execution role statement 4 exempts. IAM delivers its events only to the us-east-1 default event bus [verified 2026-09-27, [AWS re:Post knowledge center](https://repost.aws/knowledge-center/eventbridge-rule-triggers-iam-single-region)], so that rule sees them only when the app's region is us-east-1; elsewhere it matches nothing, and forwarding from us-east-1 is not built.
- *The detection itself.* One rule per service alarms on changes to the tamper resources by name prefix: `DisableRule`, `DeleteRule`, `RemoveTargets`, `PutTargets`, and `PutRule` on its rules; `StopPipe`, `UpdatePipe`, and `DeletePipe` on its pipes; `DisableAlarmActions`, `DeleteAlarms`, and `PutMetricAlarm` on its alarms; `DeleteMetricFilter`, `PutMetricFilter`, `DeleteLogGroup`, and `PutRetentionPolicy` on its log groups; and `DeleteResourcePolicy` on the Logs resource policy its rules deliver through. A deleted policy also blocks delivery of the event of its own deletion, so every rule also has an alarm on its `FailedInvocations` metric. Its own deploys raise these as expected. The CloudWatch rule matches on `eventSource` alone, because EventBridge's event reference documents only CloudWatch's direct alarm events, not its CloudTrail `source`. Each pipe also has an alarm on its `ExecutionFailed` metric by `PipeName` [verified 2026-09-27, [Pipes monitoring](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-pipes-monitoring.html)]; that page names no namespace, so `AWS/EventBridge/Pipes` is [unverified] until the metric reads back in dev.
- Every rule and self-watch rule targets a tamper log group through the Logs resource policy, which admits only `events.amazonaws.com`, and only with an `aws:SourceArn` naming a rule that targets that group [verified 2026-09-27 for rule targets generally, [EventBridge confused-deputy prevention](https://docs.aws.amazon.com/eventbridge/latest/userguide/cross-service-confused-deputy-prevention.html); the pending control-plane alarm proof is its live proof for Logs delivery]. Every rule pattern fits EventBridge's 2048-character limit at the longest environment name, refused at synth otherwise. `tests/integration/test_record_integrity_patterns.py` sends every synthesized rule pattern and pipe filter to `TestEventPattern`.

#### Legacy items and backfill

Findings, delivery, writer-receipt, and verdict items already in the audit table are not migrated and not read.

In step 3, after TTL is enabled and before the resource policy lands, a one-time backfill gives every item without one in the audit table and the four family tables an expiry:

- a receipt gets its payload's `created_at` plus the configured [retention](#terminal-coverage-and-retention-mandated-by-adr-081), including the principal-bearing receipts written since 2026-09-26. Only that field is read, never the full decoder, which some legacy receipts fail;
- its delivery disposition and admission, and every item in the four family tables, get their partition receipt's `created_at` plus the retention. An item whose partition has no readable receipt is an orphan and gets the backfill time plus the retention;
- a legacy item of a family that has moved out gets the backfill time plus a declared margin, which must reach past the policy deploy, so TTL removes it only once the policy is in force. Its removal, seen as a dry-run rescan that counts no moved-family keys once that expiry and the TTL window have passed (acceptance item 23), is the live proof that TTL deletion is not blocked by statement 2.

`make backfill-record-expiry` runs it with every target and the retention and margin explicit, proves the account with STS before any write, and reads and counts without writing under `DRY_RUN=1`. Before any table is resolved it reads `ADL_RECEIPT_RETENTION_DAYS` from the fixed-name conversation function's configuration and refuses a `RETENTION_DAYS` that differs. Each write is an `UpdateItem` conditioned on the item existing and having no `expires_at`, so a rerun changes nothing and no writer's expiry is overwritten. It scans the four family tables for keys and expiry only; only the receipts table's scan reads a payload, for a receipt's `created_at`. It prints per-kind counts of applied, already expiring, orphan, and failed items and the moved-family expiry as a UTC instant, never an identifier or a payload, and exits nonzero when any item failed. Any failed count (a receipt whose `created_at` cannot be read, or an unrecognized key) blocks the policy deploy in the [upgrade order](#record-family-storage-mandated-by-adr-080). It is the only update ever made to these items, and the processor's `INSERT` filter (step 2) keeps its updates and the TTL deletions that follow from reaching the processor.

### Evaluation enablement gate (ADR-079)

- `Custom::AgentCoreOnlineEvaluation`, one per family (today only `EvaluationV4Stack`), is the only owner of the family's online-evaluation configuration. It creates, updates, and deletes the configuration through the AgentCore control-plane API; no CloudFormation online-evaluation resource exists. The construct is `infra/lib/constructs/agent-quality/evaluation-gate.ts`, the provider `src/adapters/jobs/evaluation_gate`, and its rules `src/domain/evaluation/gate.py`.
- Its properties are the family's `EvaluationGateSpec.v1` and that spec's digest, so any change to the spec, the execution request included, reruns the gate.
- The configuration is named `adlytics_<env>_released_<family>`. A create refuses when a configuration of that name already exists, whoever created it, so the gate never adopts a configuration it did not make.
- **Evaluator identity.** The evaluators remain CloudFormation resources. Each one's revision is the first eight hex digits of the SHA-256 of its instructions and model identifier, and its name carries that revision. A prompt or model change therefore replaces the evaluator (CloudFormation retains the old one; delete it once the new revision is live-accepted), changes the spec, and runs the [evaluator-set change order](#release-records-and-dispatch-adr-079). The spec also carries each evaluator's full prompt digest.
- **Deploy order.** `EvaluationEvidenceStack` (the owned groups) and `EvaluationResultLinkV3Stack` (the ingress, its subscription filters, and the linker) deploy before `EvaluationV4Stack`, so the gate reads back deployed filters. The ingress takes each result's admissible configuration identifier from the turn's delivery receipt at runtime, so there is no stack cycle.
- **Assertions.** Every readback checks that the configuration is active in the intended execution state under its name, bound to the owned group, reading the input group and service, and naming the spec's evaluators, execution role, and sampling rule. It checks that each evaluator is ready with the spec's name, model, and prompt digest, and that the owned group holds every control of [result custody](../../concepts/observability.md#37-evaluation-result-custody-adr-079).
- **Calibration.** Before it enables, the gate scores every case of the family's corpus (`validation/evaluation-v4-cases.json`) through the on-demand `Evaluate` API for each evaluator the case names. A missing, errored, unlabelled, or unexpected label fails calibration. A spec is refused unless each evaluator has at least three cases, including at least one each of `known_correct`, `contradiction`, and `fluent_unsupported`. Calibration runs while the configuration is still disabled and its release record not enabled.
- **Grounded context per case ([ADR-083](../../decisions/adr-083-stream-the-agent-answer-and-govern-it-by-audit-and-evaluation.md)).** A corpus case may carry `grounded_context`, the exact document the evaluator reads; a case without one has its `trusted_assertions` joined as a bulleted list. The `fluent_unsupported` cases `omits_a_mandatory_qualifier` and `presents_a_top_n_list_as_complete` each read a real `GroundedEvaluationContext.v2` document and expect `grounded_correctness` Unsupported or Partially Grounded, so calibration measures the answer obligations that no longer block release. The grounded-correctness prompt names `GroundedEvaluationContext.v2`, so the evaluator revision changes and the gate recalibrates on deploy.
- **Inference and claim-free turns ([ADR-082](../../decisions/adr-082-govern-the-agent-by-evaluation-and-audit-not-text-heuristics.md), live-accepted in dev 2026-09-28).** Grounded correctness scores a figure correctly derived from the turn's evidence as grounded, and a turn that makes no platform or customer claim as "Not Applicable". The V4 corpus gains a `clarification` case expecting "Not Applicable", and derived-figure cases: a correct percentage change (Grounded, Consistent), a wrong one (Unsupported, Contradictory), a derivation across incompatible bases (Unsupported or Partially Grounded, never Grounded: the judge names the incompatible bases every time but splits between the two labels, about 3 to 1 in dev samples on 2026-09-28, since the inputs themselves are supported), and a labelled projection (Grounded). Grounded correctness therefore uses a categorical scale (Grounded, Partially Grounded, Unsupported, Not Applicable), and the other two dimensions stay numerical. A dev probe with throwaway evaluators settled the choice [verified 2026-09-27]: numerical option values must be zero or greater; the service returns the raw value, not one rescaled to 0–1 (a 0–4 scale returned 4.0 and 3.0); a not-applicable option sharing a value with another option came back as that option's label; and a categorical scale returned "Not Applicable" for a claim-free clarification, "Unsupported" for an invented customer claim, and "Grounded" for a correctly derived percentage, each with a label and no score. `EvaluationResult.v3` therefore records a completed result by its label, with a score only when the evaluator's scale is numerical, and the ingress completes a result that has a label and either no score or a score the scales declare.
- **Known limit.** The ingress completes any result that has a label and no score, whichever evaluator produced it. The delivery receipt names no evaluator's scale kind, so a numerical evaluator's result that arrives without a score is stored as completed rather than failed.
- **Known limit.** An evaluator's revision is a digest of its instructions and model identifier, not its rating scale, so a scale-only change would keep the revision its verdicts carry. Every scale change here ships with a prompt change, so the revision still moves.
- **Create** writes the release record not enabled and reads it back, creates the configuration `DISABLED` bound to the owned group, waits for it, and asserts. When execution is requested it calibrates, sets `ENABLED`, waits, asserts again, and only then writes the release record enabled and reads it back.
- **Update** replaces the configuration when the live one is missing or has another name; the new physical identifier makes CloudFormation delete the old one. Otherwise, when execution is not requested, it writes the release record not enabled, then sets the configuration `DISABLED`, rebinds it, and asserts. When execution is requested and the configuration is already `ENABLED`, every assertion holds, and the release record names exactly this configuration and evaluator set, it is left running and recalibrated, so a routine deploy opens no evaluation gap. Any other state follows the evaluator-set change order.
- **Delete** writes the release record not enabled if it enables this configuration, disables the configuration, deletes it, waits until it reads as absent, and then deletes the record. A record that enables another configuration, a replacement's, is left alone.
- **Fail closed.** Any failed assertion, calibration, or call fails the resource. Once enabling has begun, a failure writes the release record not enabled and then disables the configuration. The Reason names only assertion, evaluator, and case names, never a prompt, question, answer, or evaluator explanation.
- **Deadline.** The provider starts no control-plane call, poll, or `Evaluate` call within four minutes of its 15-minute Lambda timeout, and answers `FAILED` instead of timing out. Only the fail-closed record write and disable run past that point. It answers CloudFormation exactly once, and never `SUCCESS` before its readback.
- **Invocation.** The provider's resource policy denies `lambda:InvokeFunction` and `lambda:InvokeAsync` to every principal whose `aws:PrincipalArn` is not the stack's CloudFormation execution role, except Lambda's own service principal, and the function makes no asynchronous retries, so no other caller and no retry reruns a gate. CloudFormation invokes as its execution role, asynchronously; Lambda then re-evaluates the policy as itself when it runs the event, and without that exemption drops every callback [verified 2026-09-27, the first dev gate deploy and a probe stack].
- If the service refuses the owned group, evaluation stays disabled and the deploy fails. There is no fallback to the service-created group.
- Execution is requested per family, today by `onlineEvaluationV4.executionRequested` in `infra/lib/config`, read from `ADLYTICS_ONLINE_EVALUATION_V4_REQUESTED`. It defaults to not requested, and synth refuses it outside dev.
- **Parameters.** `EvaluationEvidenceStack` publishes the owned group name as `/adlytics/<env>/evaluation/result-log-group-v4`. The evaluation stacks' earlier result-group and configuration-identifier parameters are removed in the same deploy pass, a deliberate deviation from ADR-079 §6 recorded in its amendment. Verdicts linked before the gate stay where they are and are not read.

### Release records and dispatch (ADR-079)

- **Release record.** Each family's gate is the only writer of one SSM parameter, the family's release record `/adlytics/<env>/evaluation/release-<family>`, an `EvaluationRelease.v1` document. It says whether the family is enabled and, when it is, names the configuration identifier and the evaluator set with each evaluator's identifier, name, revision, model identifier, and prompt digest; a record that is not enabled names neither. It says enabled only after the gate read back `ENABLED`. The gate provider creates and deletes it; no CloudFormation resource declares its value.
- A missing release record means not enabled. A write, delete, or label change of a release record by any principal but a current family's gate provider role raises the [release-record alarm](#record-family-storage-mandated-by-adr-080).
- **Admission.** The conversation route admits every released turn to the outbox whenever the evaluation plane is provisioned. It reads no release record and has no evaluation setting of its own. Its outbox grant and table name render whenever the plane is provisioned.
- **The dispatcher is the switch.** The outbox dispatcher reads every release record named in `ADL_EVALUATION_RELEASE_PARAMETERS` once per run, before it claims any row, and applies the [dispatch rule](#evaluation-states-dispatch-and-provenance-adr-079). A record it cannot read fails the run. Nothing else decides what reaches evaluation.
- **Ingress.** The result ingress admits a result only when its configuration identifier and evaluator match the turn's dispatched delivery receipt, and stamps the verdict's provenance from that receipt. It reads no release record.
- **No-dispatch alarm.** An alarm fires when a family is enabled and the dispatcher has sent no turn for a configured interval while turns complete ([quality over time](#quality-over-time-adr-079)).
- **Wiring probe.** `make accept-evaluation-custody`'s `wiring` check reads, on demand, each release record against its configuration's deployed execution state; its dev result is in the [implementation status](#record-family-storage-mandated-by-adr-080).
- **Changing a family's evaluator set** follows one order: the gate writes the release record as not enabled, disables the configuration, updates and calibrates the evaluators, enables the configuration and reads it back, and only then rewrites the release record. Because evaluator identity derives from the prompt and model, a prompt or model edit is such a change.

### Evaluation states, dispatch, and provenance (ADR-079)

- **Dispatch rule.** For each due row the dispatcher decides, in this order:
  1. no family is enabled at this run: `not_dispatched` with `evaluation_not_enabled`;
  2. the turn's delivery disposition ([ADR-063](../../decisions/adr-063-record-delivery-disposition-for-released-turns.md)) says the user received the answer: the row is sent;
  3. any other disposition: `not_dispatched` with `answer_not_received`;
  4. no disposition yet: the row waits, rechecked without counting an attempt, until its admission time plus the conversation function's timeout plus 120 seconds (`ADL_EVALUATION_DELIVERY_WAIT_SECONDS`), then ends `not_dispatched` with `delivery_unknown`.
- A sent row's `EvaluationDeliveryReceipt.v2` is `dispatched` and names every family enabled at that run, each with its configuration identifier and its evaluators' identifiers, names, revisions, model identifiers, and prompt digests.
- **Not dispatched.** Every other outbox row, including one whose family was disabled after admission, ends in the terminal not-dispatched state and receives the outbox's delivered-row expiry. A later re-enable never sends it.
- While a family is disabled, released content still waits in the outbox until that expiry. That bounded custody is the stated cost of keeping the decision out of the route.
- **Evaluation state.** `QualityEvaluationReview.v3` reports one state per turn. The expected evaluators are those on the turn's delivery receipt, so the review function needs nothing from stacks that deploy after it. The projection also carries `expected_evaluator_count` and `reported_evaluator_count`, both 0 for a turn with no dispatched receipt.

  | State | When |
  |---|---|
  | `pending_delivery` | the turn was admitted and has no delivery receipt yet |
  | `results_available` | the receipt is dispatched and every evaluator on it has reported |
  | `partial` | some, not all, of those evaluators have reported |
  | `pending_writer` | none has reported and the writer receipt is absent |
  | `pending_evaluators` | the writer receipt exists, none has reported, and the deadline has not passed |
  | `overdue` | as above, past the receipt's decision time plus `ADL_EVALUATION_RESULT_DEADLINE_SECONDS` (`evaluationResultDeadlineSeconds`, 1800 in the typed configuration; the review function refuses to run without it) |
  | `not_selected` | with reason `not_admitted` (no admission), `predates_evaluation_gate` (an `EvaluationDeliveryReceipt.v1`), or the receipt's not-dispatched reason |

- **Verdict provenance.** Every stored `EvaluationResult.v3` carries the family, configuration identifier, evaluator revision, model identifier, and prompt digest, which the ingress takes from the turn's delivery receipt. A late result therefore keeps the revision it was produced under and is not refused after a later disable.

### Regression path (ADR-079)

One runner, in two modes, plus the live acceptance probes, is the regression path. Evaluator mode is built into the gate. Agent mode is implemented and ran in dev on 2026-09-28 ([validation results](../../../validation/RESULTS.md)).

- **Evaluator mode.** Each evaluator ships with a fictional calibration corpus, which the gate scores through the on-demand `Evaluate` API ([calibration](#evaluation-enablement-gate-adr-079)). A failed expected outcome blocks the evaluator. The gate runs it before it sets `ENABLED` and on every deploy that leaves a family running, so a direct deploy cannot skip it.
- **Agent mode.** A versioned fictional question set runs through the deployed dev conversation route before and after a prompt, contract, tool, or model change. The released evaluators score each answer, and the change records expected-versus-actual outcomes.
  - The set is `validation/agent-regression-v2.json` (`AgentRegressionSet.v2`, which keeps the v1 questions unchanged). Each question names the labels each evaluator dimension may return, and every question targets the synthetic fixture. A new or edited question is a new set version.
  - **Primed questions (ADR-147).** A v2 question may carry a `prime`, a turn in its own earlier conversation that seeds a figure into the persona's long-term memory, and must then carry a `precondition`: a fixture fact, grain, and period from closed allowlists. The run goes in six stages:
    1. Precondition: before any turn, one CHAT-workgroup count per preconditioned question. A count above zero marks the question unscored `fixture_drift`, and its prime does not run. A failed read stops the run before any turn.
    2. Every unprimed question, concurrently, so no prime marker is in recall while they run.
    3. Each prime in sequence, with a fresh `REGRESSPRIME-<hex>` marker per prime per run. A prime is seeded only when it scored, every expected dimension matched, and its audit receipt holds a succeeded `measurement_*` step; otherwise the question is unscored `prime_not_seeded`.
    4. Settle: wait up to 600 seconds after the last prime for a record carrying that prime's marker in the cross-session semantic namespace the Harness retrieves. A failed list request is retried at the next poll until the bound. A prime with no such record by the bound marks its question unscored `memory_settle`, and the run still writes its report. A poll that reads its 20-page budget and still holds a `nextToken` has failed too, as `PageBudgetExhausted`. When the last poll before the bound failed, the report also carries `prime_settle_error` with that failure's error type, so a record that could not be read is not mistaken for a prime the strategy never processed.
    5. Every still-scorable primed question, concurrently.
    6. Teardown: remove every prime-marker record. A teardown that times out or fails still writes the report, with `prime_teardown: "incomplete"`, and the run exits 1 whatever the scores.

    Primes count toward neither the match count nor the comparison. The marker match is harness readiness and cleanup; it never reads or gates an answer (ADR-082).
  - **End-to-end evidence.** When the current report ran primes, the comparison adds `end_to_end`: a primed question is `fixed` only when the baseline scored it with grounded correctness `mismatched` and this run scored and matched it. Every other primed question is `pending` with its reason: `baseline_unscored`, `baseline_not_mismatched`, `current_unscored`, or `current_not_matched`.
  - Known limit: the prime's memo marker stays in recall while the primed questions run. Before a post-fix mismatch counts against the fix, or before any revisit of an output gate, read that session's evaluator result to confirm the unsupported claim was a figure.
  - `make regress-agent` runs the set through the same chain the acceptance probe attests: the turn, its receipt, the delivery receipt, and one provenance-stamped verdict per dispatched evaluator. It then maps each verdict to its dimension by the evaluator name's dimension segment.
  - It writes an `AgentRegressionReport.v1` into local evidence custody: per question, the terminal, the observed label per dimension, whether it matched, and a match count. It records no question text beyond the set's own fictional text, no answer text, and no evaluator explanation.
  - Given a baseline report from before the change, it lists each question that matched before and not now, and each that improved. A run exits zero once every question's chain is attested, whatever the labels. The model is nondeterministic, so the owner reads the report and decides; a label mismatch never blocks by itself.
  - Every question must be scored, so the runner refuses to start unless a family is enabled and each enabled configuration samples 100% of sessions. Questions run concurrently (four by default), because the service delivers verdicts in batches minutes apart, and each waits up to 30 minutes for its own. Audit, delivery, and verdict reads use increasing 2, 3, 5, 8, then capped 13-second intervals rather than a fixed hot poll. A question whose chain could not be attested or whose turn was not dispatched is reported as unscored with its fixed stage marker, including `transport` and `timeout` for a broken or stalled stream; the others are still reported, and the run then fails. Each question takes a fresh access token from the refresh cookie, since a run outlives the 15-minute token. The baseline is read and checked before any turn runs, and a report of another set version is not compared.
  - After a successful run the raw turn frames beside the report are removed unless `RETAIN_EVIDENCE=1`; a failed run keeps them for diagnosis.
  - When an evaluator change ships with an agent change, deploy the evaluation stack first and take the baseline with the unchanged agent, then deploy the agent change and rerun. Otherwise the comparison mixes the two changes. ADR-082 is such a change.
  - Known limit: each question runs once per invocation, so one run cannot separate a regression from ordinary variance. Repeat the run to see that.
- Whether `Evaluate` accepts this repository's released-response span shape is [unverified] until the gate's dev run records it. Batch evaluation over the input group, the named fallback, is not built. If `Evaluate` refuses, the gate cannot calibrate, so evaluation stays disabled and the gap is recorded for the owner; an evaluator is never enabled on absent calibration evidence.

### Quality over time (ADR-079)

`EvaluationQualityStack`, last in `DEPLOY_ORDER`, renders a dashboard and four alarms over the
current V4 evaluators. It is destroyable and holds no record.

- **Verdict counts come from the result linker.** For every newly linked completed verdict, the
  linker emits `Adlytics/EvaluationVerdict` twice: once by `Dimension` and `Label`, and once by
  `Dimension` alone, the total. The dimension is the evaluator name's dimension segment and the
  label its normalized scale label, both from the closed vocabulary in
  `domain/evaluation/quality.py`. Anything outside it counts as `other`, and an exact replay is not
  counted again.
- **AgentCore's own metrics cover numerical scores only.** It publishes one metric per evaluator in
  `Bedrock-AgentCore/Evaluations`, named by the evaluator, whose value is the score and whose sample
  count is the verdict count. A categorical evaluator, such as grounded correctness, has no series
  [verified 2026-09-29, dev `list-metrics`: none for the current grounded evaluator while its
  results were landing]. The dashboard uses those metrics only for the two numerical evaluators'
  average score.
- The stack derives each evaluator's name from the same specs, prompt files, and model identifiers
  `EvaluationV4Stack` uses. After a prompt or model change, `EvaluationQualityStack` must be
  redeployed with it, as the full `DEPLOY_ORDER` pass does, or the average-score graphs keep the old
  evaluator's name.
- **Dashboard** `adlytics-<env>-evaluation-quality`, in this order:
  - per evaluator, verdicts by label, and the average score for the two numerical scales;
  - each evaluator's worst-label share;
  - coverage: admitted, dispatched, each withheld reason, retries, and verdicts per dimension;
  - the four pipeline functions' errors and the two dead-letter queues;
  - the alarm states.

  It carries no turn identifier. The review API's `turns` and `turn` routes remain the surface for
  listing and reading turns.
- **Worst-label alarms**, one per evaluator: the share of its verdicts labelled `Unsupported`
  (grounded correctness), `Contradictory` (internal consistency), or `Poor` (helpfulness), above
  0.2 over six hours. Below five verdicts in the period the expression yields no data point, so the
  alarm reads insufficient data rather than OK. The values are `evaluationQuality` in
  `infra/lib/config`. The alarm reports a trend; it never gates a release.
- **No-dispatch alarm** `adlytics-<env>-evaluation-no-dispatch` fires when three consecutive
  30-minute periods each admitted a turn, dispatched none, and withheld none as
  `evaluation_not_enabled`.
  - A disabled family withholds every admitted row with that reason, so it does not trip the alarm.
  - These do trip it:
    - a dispatcher that has stopped running, whether or not a family is enabled;
    - an enabled family's dispatcher that sends nothing;
    - periods in which every admitted row was withheld because the answer was not received or its
      delivery was never recorded. The coverage graph shows which of these it is.
  - It needs three periods because CloudWatch also evaluates the unfinished newest period, and a
    dispatch lags its admission by minutes. With three, a breach needs one whole period between two
    others.
  - The denominator is `EvaluationAdmission`, which the conversation route counts once per new
    outbox admission, never for an exact replay. It has no dimension.
- Every alarm notifies the published alarm topic.
- **Not built:** span-to-verdict latency. It is 434 to 675 seconds in dev because the service
  returns results in five-minute batches [verified 2026-09-29].

Acceptance (dev), all six passed on 2026-09-29
([validation results](../../../validation/RESULTS.md#evaluation-quality-over-time-adr-079--2026-09-29)):

1. The dashboard exists and names the current numerical evaluators' metrics and the verdict counts.
2. Each alarm reads back with the configured expression, threshold, and periods.
3. `aws cloudwatch set-alarm-state` on the no-dispatch alarm and on one worst-label alarm executes
   its action on the alarm topic, and each returns to its evaluated state.
4. After the item 5 run, each dimension's `EvaluationVerdict` total rose by the verdicts linked,
   and alarm history shows each worst-label alarm evaluated to `OK` or `ALARM` from those
   verdicts. The run starts well inside a six-hour period, so its verdicts are not split below the
   minimum across two.
5. `make regress-agent` records a baseline with every question scored.
6. Replaying the no-dispatch expression over the dev traffic since the deploy with `GetMetricData`
   yields no run of three consecutive breaching points, and `EvaluationAdmission` and
   `EvaluationDispatch` `dispatched` track each other. A single breaching period is expected when
   a turn's dispatch lands in the next period. A breach is proven by unit test, never by stopping
   the live dispatcher.

### Terminal coverage and retention (mandated by ADR-081)

- An inbound guardrail intervention, a refused exchange, and a client disconnect mid-stream each have a closed terminal outcome and write a receipt. The receipt write runs on every exit path.
- A failed turn keeps the trajectory it reached.
- The disconnect receipt carries `client_disconnected`, the trajectory reached, publication `published` when text was sent and `not_applicable` otherwise, the character count of the text the consumer took, and no evaluation admission. It derives no finding.
- A killed function still leaves no receipt. Audit coverage measures that gap.
- The inbound intervention and refused exchange receipts carry the closed terminal outcome `input_policy_intervention` or `exchange_refused`, the verified principal, and the server correlation, with nothing run or published: operation `none`, `not_attempted`, publication `not_applicable`, no trajectory, and no evaluation admission. Neither derives a finding. A receipt that cannot be built or written never changes the refusal the route answers with; the [terminal log line](../../concepts/observability.md#39-turn-terminal-log-adr-081) then reads `not_persisted`.
- Receipt retention is a required per-environment configuration value with no default.
- Every record of a turn, in every table of the [record-family storage](#record-family-storage-mandated-by-adr-080), carries a TTL expiry computed from the receipt's creation time and that retention.
- Writers that do not read receipts take the creation time from the message they consume, as [record-family storage](#record-family-storage-mandated-by-adr-080) states.
- TTL deletion runs some time after expiry, so every reader treats a record whose expiry has passed as absent.
- Records written before this retention get their expiry from the [legacy backfill](#legacy-items-and-backfill).

What of this section is deployed is stated in the [record-family storage implementation status](#record-family-storage-mandated-by-adr-080).

- The retention is `receiptRetentionDays` in `infra/lib/config`, read at synth from `ADLYTICS_RECEIPT_RETENTION_DAYS`. Absent, synth refuses; present, it must be a positive whole number of days. The dev deployment declares 90.
- Each record writer receives it as `ADL_RECEIPT_RETENTION_DAYS`: the conversation route, the processor, the outbox dispatcher, the evaluation writer, and the result linker. Each refuses to start without it, and a store built without a retention refuses to write.
- `expires_at` is a Number attribute of whole epoch seconds, outside the attested payload: the receipt's `created_at` plus the retention, truncated toward the past, so every writer computes the same second from the same receipt. It is part of the exact-replay comparison, so a replay that would change it is a conflict.
- A reader compares a stored `expires_at` with its clock and reads a record past it as absent; an item without one reads as unexpired. An expired receipt, or an index key whose receipt TTL has already deleted, is left out of correlation discovery even while its index key remains, and still counts toward the discovery bound.

The support reference and server-minted correlation identifier are owned by the [Conversational Runtime](../conversational-runtime/low-level-design.md#turn-reference-and-correlation-adr-081).

### Target acceptance (mandated by ADR-079, ADR-080, and ADR-081; not yet implemented)

Live dev acceptance reads each outcome and records only counts, states, and error classes, never record values:

1. **Deploy order.** A deploy in the typed order reaches each gate with the result ingress's subscription filter already on the owned group.
2. **Gate refusal.** With one result-group control made to fail in dev before a deploy (for example, a second subscription filter on the group), the deploy fails, the configuration reads back `DISABLED`, and its release record reads not enabled. Removing the fault and redeploying enables it.
3. **Gate enable.** With execution requested, the configuration reads `ENABLED` and its release record reads enabled with the configuration identifier and the evaluator set. The wiring probe reports agreement.
4. **Gate disable.** With the request turned off for an enabled family, the redeploy leaves the release record reading not enabled and the configuration `DISABLED`, and the gate's run log records the release-record write before the state change. The wiring probe reports agreement.
5. **Evaluator-set change.** A fictional evaluator revision change's gate run log records, in order, the release record written not enabled, `DISABLED`, the update and calibration, `ENABLED` read back, and the release record rewritten with the new evaluator set.
6. **The route admits every released turn.** With the evaluation plane provisioned, a fictional released turn writes an outbox row whether or not its family is enabled. A synth test asserts the route renders no release-record read and no evaluation setting.
7. **Dispatch while enabled.** With a family enabled, a fictional delivered turn's row is sent, and its delivery receipt records the configuration identifier and the evaluator set of the release record in force at that run.
8. **No dispatch while disabled.** With the family's release record not enabled, and separately with it absent, a fictional delivered turn's row ends in the terminal not-dispatched state carrying the delivered-row expiry. After the family is re-enabled, that row is still not sent.
9. **Not-dispatched rows expire.** A fictional turn whose stream the client aborts leaves an outbox row in the terminal not-dispatched state, carrying the delivered-row expiry, and it is never sent.
10. **Late result keeps its provenance.** A result for a fictional turn sent before the item 5 change, arriving after it, is linked by its delivery receipt's configuration identifier and carries that receipt's evaluator revision, model identifier, and prompt digest, not the new set's. A unit test shows a result whose configuration identifier does not match the delivery receipt is not linked.
11. **Release-record writer and dispatch alarms.** The control-plane rule pattern matches a release-record write or delete by any principal but the gate provider roles, and not the gates' own, with a unit test for each. `aws cloudwatch set-alarm-state` on the no-dispatch alarm reaches the alarm topic, and its expression has a unit test for an enabled family with completing turns and no sends.
12. **Policy ordering.** Across the slice's deploy, the processor, dispatcher, writer, and linker dead-letter queues show zero growth, so no old writer's write failed while the policies landed.
13. **Processor untouched by the backfill and TTL.** The processor's stream mapping reads back filtered to `INSERT`. Across the backfill and the TTL deletions of item 23, the processor records zero retries and zero finding writes.
14. **Non-writer writes.** On each table, `PutItem` by a principal whose identity policy allows it but which is not the writer is refused with the resource policy's explicit deny.
15. **Mutations.** On each table, `UpdateItem`, `DeleteItem`, and `BatchWriteItem` by that principal are refused with an explicit deny, and a synth test asserts statement 2 names no principal exception, so the writer is refused too.
16. **Data copy.** On each table, `CreateBackup` and `ExportTableToPointInTime` by a principal whose identity policy allows them are refused with an explicit deny, and a synth test asserts statement 3 names no principal exception and every statement covers the table's indexes.
17. **Receipt reads.** `GetItem`, `Query`, and `Scan` on the receipts table by a principal that is not a named reader are refused with an explicit deny.
18. **Read back.** A replayed writer item is reported as an exact replay, not redriven.
19. **Tamper alarm wiring.** `aws cloudwatch set-alarm-state` on each item-change alarm, on the control-plane alarm, and on the function-change alarm reaches the alarm topic. The pipe filter and the metric filter have unit tests with `MODIFY`, `REMOVE`, and TTL `REMOVE` samples, where only the first two match. The function-change rule pattern has a unit test per watched action for a function holding a named role. The item-change alarms stay `OK` across the backfill. No policy is weakened to produce a real change.
20. **Control-plane alarm.** The deploy check names the logging trail or reports that none is logging. With a trail logging, a successful deploy-driven change to a record table (for example, the receipts table's deletion protection landing through CloudFormation) raises the control-plane alarm, and the deploy record acknowledges it. A refused call is not attributable to a table: CloudTrail records a DynamoDB control-plane call denied by the policy with no request parameters and no resources [verified 2026-09-27, five refused `UpdateTimeToLive` calls], so the rule sees only calls that succeed. That is the calls that matter, because a refused call changed nothing; refused calls stay visible in CloudTrail itself.
21. **Terminal receipts.** A fictional inbound guardrail intervention, a refused exchange, and a client disconnect mid-stream each write a receipt, and `turn` returns each with its closed terminal outcome; the disconnect receipt's trajectory and released character count match what the turn reached and sent. All three are deployed; the intervention receipt is dev accepted, and the refused-exchange and disconnect receipts are covered by unit tests only, because neither can be produced from outside in dev ([implementation status](#record-family-storage-mandated-by-adr-080)).
22. **Retention through the API.** Every record `turn` returns for a fictional turn carries an expiry equal to its receipt's creation time plus the dev retention. A fictional turn written just before the slice deploy, so its backfilled receipt is still inside dev retention, is returned by `turn` with its creation time plus the dev retention. Each table's TTL reads back enabled on that attribute.
23. **TTL under the deployed policy.** The policy deploy completes before the earliest moved-family expiry the backfill set, the `moved_family_legacy_expires_at` it printed. After that instant, the table's `TimeToLiveDeletedItemCount` reaches the backfill's moved-family count while receipts remain readable through the review API, and the item-change alarms stay `OK` across those deletions. The receipts read deny refuses an operator's rescan, so the metric is the proof. If any moved-family key remains, TTL under the deny has failed and the design is revisited.
24. **Expired as absent.** Unit tests show every reader treats a record past its expiry as absent.

## 9. Risks and open questions

- A deployment where the [retention](#terminal-coverage-and-retention-mandated-by-adr-081) is not deployed, or the [legacy backfill](#legacy-items-and-backfill) has not run, holds records with no expiry; which deployments that covers is stated in the [implementation status](#record-family-storage-mandated-by-adr-080). Reader access policy, aggregate cost/cardinality, evaluation selection, and sampling policy remain local controls requiring explicit operational review.
- TTL deletion proceeds under a resource policy that denies `DeleteItem` to everyone [verified 2026-09-29, acceptance item 23].
- The evaluation service writes to the customer-owned result group under its default encryption, and the ingress's subscription delivery from that group reaches it under the ingress's resource policy: each dev `accept-evaluation-link` turn on 2026-10-02 completed with 3 verdicts ([validation results](../../../validation/RESULTS.md#security-pre-publication-fixes-on-dev--2026-10-02), A4 and A5). Whether the service needs the execution role's write grant to do so stays [unverified], because the role still holds it. The gate's readback cannot observe any of these: a failure leaves results absent, which the review reports as `overdue`, and there is no fallback group.
- A multi-turn released-session contract is not defined; quality records remain terminal-turn scoped.
- A missing external evaluation result is a pending or failed delivery observation, never a synthetic score or retry trigger.
- Sanitized acceptance conclusions are owned by [validation results](../../../validation/RESULTS.md).
