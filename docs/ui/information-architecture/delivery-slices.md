## 1. How to read this

Each slice is vertical: server, contract and page ship together, so one slice gives a user something
they can check on dev. A slice closes only when its dev probe passes, and every earlier slice's probe
is re-run as a regression gate before the next slice starts. Evidence is kept in two separate columns,
because a passing unit test or local check never stands in for live behaviour on dev.

## 2. Rules for every slice

1. **Server first, then the frontend.** Each slice deploys the API stack, then publishes the frontend
   with `make build-frontend` (`scripts/build-frontend.sh`). New response fields ship with their
   artifact or render-format bump before any bundle reads them. A server that gains a request version
   accepts the old and new versions for one release; the browser moves to the new one in the same
   slice; a later slice removes the old one. From Slice 11 the `/me` body is exactly four keys and
   the browser refuses any other shape ([ADR-115](../../decisions/adr-115-organise-the-app-into-customer-question-hubs-from-one-navigation-file.md)
   decision 8). This replaces the earlier two-or-three-key dual accept. The orchestrator approved it
   on 2026-10-08 under the owner's delegation, and it rests on the owner's simplified-delivery
   approval of the same day: transitional dual-format reads retire because the API, a full re-bake
   and the frontend deploy together on dev, which has no users but the owner. The accepted
   consequence: whenever this bundle meets a two-key server (an API rollback, a partial API deploy
   or the frontend published first), every signed-in user sees "Session status is unavailable" on
   every page until the API is fixed forward. The bundle published before Slice 11 accepts only the
   two-key body, so the frontend is published straight after the API, and until then that bundle
   shows the same message.
2. **No dual path.** A replaced surface retires in the slice that ships its replacement, and
   only-retired surfaces wait for the cleanup slice, Slice 12
   ([ADR-117](../../decisions/adr-117-keep-pages-and-apis-only-on-merit-and-retire-a-replaced-surface-with-its-replacement.md)).
   This plan lists each slice's proposed retirement scope only. The retirement inventory and the
   clean-replacement rules stay in [Workspace implementation cutover](../implementation-cutover.md),
   which gains a row for each scope when the ADR is accepted.
3. **Tokens at the source.** New design tokens go into `frontend/app/globals.css`, never into a
   component.
4. **Conformance on the deployed page.** The slice's pages are compared with their approved mockup
   states on dev, with real data, at 1440, 1280, 1248, 1180, 1100, 1024, 1008, 881, 880 and 768 px in
   both themes: zero axe violations, no sideways scrolling, no text under 12 px, and a side-by-side
   screenshot review of every state the mockup shows
   ([ADR-118](../../decisions/adr-118-render-every-page-from-one-set-of-shared-patterns-and-extended-tokens.md)
   decision 10). Where an ADR rule overrides a mockup state, the build is checked against the rule.
   States the data can't produce on dev, such as a partly reported day, are shown with unit fixtures
   and recorded as unit-proven only.
5. **Approvals.** An `infra/` change starts only when its approval is recorded for that slice, dev
   only. The `retail-health-product` route (Slice 7) and the 404 allowlist (Slice 2) are approved.
   Every other infrastructure change below needs its own approval.
6. **Probes.** Use an existing probe when it settles the question; add one only when none can.
   Probes take every target input explicitly, and published results follow `validation/RESULTS.md`
   custody rules.
7. **Local checks.** `make check` passes before any deploy.
